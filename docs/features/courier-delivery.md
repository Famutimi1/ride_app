# Courier delivery

Courier is a separate booking flow, not a passenger ride with a different label. The sender enters a package description, weight (up to 5 kg), recipient name and international phone number, and optional handoff instructions. The package must be sealed; the sender confirms that it contains no cash, weapons, drugs, hazardous goods, live animals, or other prohibited items. Both the sender and recipient meet the driver at the vehicle. These choices follow the handoff pattern described in [Uber Connect](https://www.uber.com/us/en/blog/uber-connect-ondemand-package-delivery/) and [Bolt Delivery](https://bolt.eu/en/support/articles/360010946899/), with a deliberately smaller 5 kg limit for this initial service.

The sender selects pickup and delivery addresses, sees the courier tariff, and pays from their wallet. Cash is not offered because the sender and recipient are different people. The wallet hold occurs when the order is placed, and settlement uses the existing append-only ledger. The courier tariff in migration `005_courier_trips.sql` is a **development placeholder** and must be reviewed before commercial use.

Courier records reuse the `trips` table, dispatch queue, active-trip guards, status history, and named trip socket room. `service_type='courier'` and validated `courier_details` distinguish them from rides. No new table or dependency is introduced. Only approved drivers who enable **Package deliveries** on their dashboard receive courier offers; the default is off.

The driver marks arrival, confirms package collection, and follows the live trip to the recipient. The sender sees a six-digit handoff code and shares it with the recipient. The driver enters the code only after handoff; settlement and `completed` happen together in one database transaction. The code is derived server-side from the trip ID and access-token secret with domain separation, never stored in plaintext or included in the driver offer. Five incorrect attempts lock verification; the sender can generate a new code up to twice. Rotating the access-token secret during an active delivery changes the code, so secret rotation requires operational coordination.

If the recipient cannot receive the package, the driver can start a return. The trip moves from `in_progress` to `returning`; location tracking and the driver's busy status remain active. The driver navigates back to pickup, hands the package to the sender, and enters the same current handoff code. The trip becomes `returned` and the original delivery fare settles; there is no added return surcharge in this implementation. After the package has been collected, the order cannot be cancelled as an ordinary ride because the package must be accounted for through delivery or return.

Migrations `005`–`009` are applied in the local development database. The local backend must be rebuilt and restarted after these changes. Before launch, operations should review the tariff, restricted-item policy, delivery radius, return handling, customer support for lost packages and exhausted code resets, and driver onboarding terms. This implementation does not include insurance, package photography, or recipient SMS; the sender shares the code through their own channel.
