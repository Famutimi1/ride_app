# Payments and ledger gap report

The current production write path is `backend/src/modules/trips/settlement.service.ts` → `wallet_transactions`. This is an append-only **single-entry** table. Balances are `SUM(amount_kobo)` by `user_id`. Wallet trips debit the rider only at completion; cash trips debit driver commission. There is no fare hold, earnings/wallet separation, payout, reversal, top-up, Paystack webhook, or reconciliation. The only existing rows in the connected development database are two driver cash-commission debits (−233,940 kobo total) and their two platform credits. No withdrawal rows exist. Existing migrations are `001_auth.sql` and `002_trip_system.sql`.

Migration plan: create the three double-entry ledger tables and payment tables; seed system accounts; post one opening adjustment per nonzero **user/account kind** balance. Classify legacy rider fare debits as wallet activity and legacy driver earning credits or cash-commission debits as driver earnings. This preserves both envelopes for someone who rode and drove. Compare every migrated user/account balance with the old sum before retiring the old writer. Keep the old table as read-only audit history, block new inserts, and route all future money movements through `payments/ledger.service.ts`. The connected development data's negative driver balance needs a debit to driver earnings and a credit to `expense_adjustments`. Verify the old and new totals to the kobo before app rollout. An unapproved user with a negative driver balance needs manual review rather than an automatic earnings account.

The spec's operational questions remain open: live Paystack transfer/OTP/manual-settlement settings, real payment limits and fees, and the wallet's regulatory/tax treatment. Development settings will be clearly labelled placeholders and no live transfer is enabled without a Paystack secret key.
